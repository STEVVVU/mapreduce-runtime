# Initial hosted MapReduce measurements

The changed runtime completed the frozen 960-job sustained workload with exact results. The earlier implementation overloaded on the same input, and a separate native profile confirmed full-registry durable saves as its limiter. These were different hosted CPU models. No exact causal speedup ratio is claimed.

These resource values derive from 100 ms /proc samples and recorded CLK_TCK=100. Neither sustained row is a repeated estimate, and CPU model differences prevent an exact performance-gain attribution.

The separate five-child native profile directly attributes 74.97% of coordinator samples to full-registry save, 55.48% self to JSON encode; workers were about 91% idle. These are sampled profile proportions, including idle, not throughput numbers. The fix saves only the mutated job atomically, preserves legacy metadata by import/authoritative overlay, and keeps attempts/results durable before the referencing metadata and response. It changes no leases, retry bounds or output semantics. Both correctness/recovery and the complete frozen after campaign passed. The O(N) in-memory claim scan, growing retained state and single coordinator disk remain limits. A same-runner interleaved established-tool comparison is still required before claiming a numerical speedup or maximum capacity.
